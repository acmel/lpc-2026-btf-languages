Extending BTF
to support more languages




Alan Maguire, Arnaldo Carvalho de Melo
Linux Plumbers Conference 2026
eBPF Track

Why now?


  • Kernel modules can be built in Rust
  • BTF was designed around C
  • Time to assess non-C constructs
  • Rough suggestions to trigger discussion

C: simple



  struct point { int x; int y; };
  enum color { RED, GREEN, BLUE };
  • Struct → BTF_KIND_STRUCT
  • Enum → BTF_KIND_ENUM (plain integers)

Rust: rich



  enum Option<T> { Some(T), None }
  enum Result<T, E> { Ok(T), Err(E) }
  • Enums with data: tagged unions
  • Discriminants, generics, zero-sized types
  • 128-bit discriminant values

DWARF: C enum



  DW_TAG_enumeration_type "color"
    DW_TAG_enumerator "RED" (0)
    DW_TAG_enumerator "GREEN" (1)
    DW_TAG_enumerator "BLUE" (2)

DWARF: Rust enum



  DW_TAG_structure_type "Option<i32>"
    DW_TAG_variant_part (DW_AT_discr -> discriminant)
      DW_TAG_variant "Some" (DW_AT_discr_value: 1)
        DW_TAG_member "0" (i32)
      DW_TAG_variant "None" (DW_AT_discr_value: 0)
  • New tags for pahole: variant_part, variant, discr_value
  • Unused in C: no support until Rust came along

LLVM already encodes it



  [1] STRUCT 'MyEnum' size=12 vlen=1
          '(anon)' type_id=3 bits_offset=0
  [3] UNION '(anon)' size=12 vlen=3
          '(anon)' type_id=2 bits_offset=0  <- discriminant
          'First' type_id=4 bits_offset=0
          'Second' type_id=6 bits_offset=0
  • STRUCT wrapper + single anonymous UNION
  • Discriminant as anonymous member + variants
  • pahole follows this shape

Don't infer: DW_AT_discr


  • rustc layout explicitly unstable
  • DWARF 5, 5.7.10: DW_AT_discr points at the member
  • Real type, real location, real size
  • Synthesize name "__discriminant" (BTF needs names)

Explicit vs niche


  • Option<u32>: tag at 0, payload at 4 → emit it
  • Option<NonZero<u32>>: tag IS the payload → emit nothing
  • Rule: emit only when it doesn't overlap the payload
  • Niche is the common kernel case (Result<(), Error>)

Unions sit at zero


  • Non-zero discriminants can't live in the UNION
  • libbpf refuses, kernel verifier rejects at load
  • Real storage → outer STRUCT (overlap legal)
  • Payload itself → dropped
  • LLVM emits what the verifier rejects: upstream bug

Pretty target



  struct Option<u32> {
      u32 __discriminant;      /*  0  4 */
      union {
          struct None {};
          struct Some { u32 __0; /*  4  4 */ };
      };                       /*  4  4 */
  };

Zero-sized, dynamically-sized


  • ZSTs: byte_size 0, member type () rewrites to 4 bytes
  • STRUCT size=0 with a 4-byte member: BRAIN FART ALERT!
  • DSTs: str/[u8] tails, member bytes > struct size
  • Fix: skip zero-size members, clamp padding math

Non-C precedent: Go, 2023


  • Trace Summit Bilbao: uprobes + BPF on Go userspace
  • Go DWARF, calling convention, perf probe for Go
  • We've done non-C DWARF before

Common need across languges - namespaces?


  • Namespacing is used extensively in Rust
  • C hierarchy is flat, most languages have deep scope/nesting relations
  • Can simulate with BTF tags, but it is wasteful; need one tag per tagged entity
  • A more structured BTF kind could represent parent-child relationships
  • Namespace as a whole could be tagged if needed

Open: the abstract's list


  • Slices / "fat pointers" with type and size
  • Generics (monomorphization explosion)
  • Interfaces (trait objects, vtables)
  • Lifetime tags
  • See: btf-for-rust-proposal.md

Compilers emit BTF too


  • GCC -gbtf (12+, default on BPF) + -mco-re
  • LLVM -gbtf + lld --btf-merge: pahole step optional, someday
  • gccrs: still out of tree
  • RANDSTRUCT: without the seed, layouts lie to every tool

Ask to the room


  • Named __discriminant already usable in CO-RE relocations
  • discr_values per variant not representable in BTF today
  • New kind? DECL_TAG-like annotations on union members?
  • Verifier tracking the active variant: match at load time

Open Questions: VARIANT_PART Design


  • Implicit fields (data_ptr, length at fixed offsets) vs Explicit (vlen=N)?
  • Discriminant type: mandatory or optional for C-style enums?
  • Size field: include discriminant in total size?

Open Questions: Vtables & Compatibility


  • Vtable method ordering: compiler consistency sufficient?
  • Backward compatibility: emit both old and new during transition?
  • Consumers ignore unknown kinds: sufficient for rollout?

Open Questions: 128-bit Discriminants


  • Current ENUM64 supports 64-bit
  • Go straight to 128-bit or incremental?
  • btf_enum128: 4 x 32-bit words sufficient?

Function tracing in Rust modules


  • Problem: ELF symbols, kallsyms for Rust module functions uses mangled Rust names
  • Example kallsyms entry for rust_print module:
ffffffffc0fec430 t _RNvXs5_NtCs1DErgtJhccC_6kernel3fmtReNtB5_7Display3fmtCs7y3Drb9gYub_15rust_print_main	[rust_print]

Solution: decl tags for mangled names


  • Have pahole use the DW_at_name, record the DW_at_linkage_name as a BTF decl tag:
[145526] FUNC 'fmt<str>' type_id=145525 linkage=static
[145527] DECL_TAG 'rust:linkage:_RNvXs5_NtCs1DErgtJhccC_6kernel3fmtReNtB5_7Display3fmtCs7y3Drb9gYub_15rust_print_main' type_id=145526 component_idx=-1

Using decl tags to trace


  • Allows for tracing a function using a stable name
SEC("fentry/fmt<str>")
  • Still supports runtime matching:
    • Find function via name
    • Use decl tag to identify attach point in kallsyms
  • See here for a PoC
